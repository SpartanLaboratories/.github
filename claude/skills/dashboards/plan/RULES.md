# Plan boards — the ruleset

A plan board is the planning-and-development record of one issue, kept true from the moment
a `/resolve-issue` run starts until the change lands: what was missing, what was considered,
what was decided, what was built, and — while the run is alive — where it is right now. The
repository work board shows every such run at once. `GUIDANCE.md` applies throughout.

The board is a **general representation with little code**. Summaries, decisions, reasons,
states and links; never listings. The detail lives in the Markdown beside it: `plan.md` is the
implementer's spec, `final-implementation.md` the as-built record, `research/` and
`architecture.md` the evidence. The board links them; it does not repeat them.

## 1. Files

```
docs/plans/<issue>-<slug>/
  plan.json           the board's data: the source of truth
  dashboard.html      the page: template + plan.json embedded verbatim; regenerated, never edited
  plan.md, impact.md, final-implementation.md, architecture.md, research/   unchanged, linked
docs/plans/
  index.html          the repository work board (template + board.json)
  board.json          every run: generated by board.js from the plan folders and the tracker
```

The footer of a board reads "Corresponds to `<folder>/plan.json`. Code and the Markdown beside
this page are authoritative on any conflict. Columns 1 to 3 are written once; column 4 records every
difference."; the work board's, "Corresponds to `docs/plans/board.json`. Code and the Markdown beside
this page are authoritative on any conflict." (`.live/board.json` on the live view). The template
writes it; nothing else goes there (`GUIDANCE.md` §3).

Levels 2–4 get a board; a level-1 issue has no plan folder and no board, and appears on the
work board only. A tracking issue (a level-4 plan) gets a board in its own folder with **one
row per unit**, each row linking to that sub-issue's own board; each sub-issue gets a full
board in its own folder.

**Links to an issue and its board** (`GUIDANCE.md` §5). One general rule, by how many links fit:

- **Number and title together: two links.** Where a board shows an issue's number beside its
  title, the **number opens the GitHub issue** and the **title opens the issue's own board**, or
  stays plain text while it has none. The **unit row** of a tracking board is the example. Its
  title line reads `1. #61 Shared build logic`: the unit's number in landing order, `#61` linking
  issue 61 on GitHub, and "Shared build logic" linking the sub-issue's board (plain while it has
  none; `1. Shared build logic` while the unit has no issue yet). Under it stay the unit's path and
  its system, and nothing else: no link line. The same pair is used by the WIP strip's "In
  progress" and "Up next" lines (`#47 java-floor`), the inspector's unit entry, the Context
  roadmap (a tracking board's units, an issue board's roadmap item and its siblings), a
  follow-up that records a `title`, and the Impact tab's unit entries; on the work board, each
  row, each group heading, each roadmap item and each unscheduled issue (§5).
- **Only one link fits: the board first.** A lone `#n` — the header's "part of" chip, the
  breadcrumb, a chain entry, a "blocked by" tag, the badge of a part deferred to an issue, a
  follow-up with no title, a blocker, any `#n` in the board's text — opens **that issue's own
  board** when one exists and its GitHub issue only while none does.
- **GitHub ↗** — the small link to the GitHub issue — sits beside a lone `#n` that opens a board
  only where the page offers no other way to reach the issue: the "part of" chip and a follow-up
  with no title. Wherever the number itself opens GitHub, there is none.

The board's own `#n` opens its GitHub issue, and `PR #n` its pull request. No link points at a
file that is not there: a board exists when its `dashboard.html` is in the same tree, and the
link is relative to the linking board's folder, so it is never dead. Where the boards sit:

- a **unit's** board is in the sub-issue's folder inside the tracking issue's folder; one kept
  elsewhere is not linked, and `check.js` warns about it;
- the **parent's** board is the enclosing folder, the parent's own (the folder layout puts a
  sub-issue's folder inside its tracking issue's); a sub-issue folder kept elsewhere does not link
  its parent's board, and `check.js` warns about it;
- **any other** issue's board may be anywhere under `docs/plans/` in the tree.

Nobody writes the board links by hand: `embed.js` sets them from the folders on disk at every embed and clears a link whose board
is gone: each unit's `unit.board` (filling `unit.folder` when it is unset), the parent's
`parent.board` (`../dashboard.html`, or `null`), and `issueBoards`, a map from every other issue
the board names to its board's path (present only while one is linked). `new.js --parent`
embeds the new board, which links its parent's board, and re-embeds the tracking board, so the
new sub-issue is linked from it at once; any other board that names the new issue picks the
link up at its own next embed (`check.js` warns on it until then). The template routes every
board link through those three. The work board applies the same rule to every issue that has a board,
a tracking issue as much as a sub-issue (§5).

Scripts, from the repo root: `new.js <issue> <slug> …` scaffolds a folder from the template;
`embed.js <folder>` embeds `plan.json`; `check.js <folder> --auto` enforces this ruleset and
checks the page against its template (§8); `board.js` regenerates `docs/plans/board.json` and
`index.html`.

**Made from the template, checked where it deviates** (`GUIDANCE.md` §3, §8). A board is always
the template plus its `plan.json`, and the work board the template plus `board.json`: `new.js`,
`board.js`, or a copy of the template and `embed.js`, and nothing else. Writing a board at an
event is therefore editing `plan.json` and re-embedding. Such a board needs no browser pass:
`check.js --auto` checks the data, the rules and the embed, confirms the page is the verified
template plus its data, and runs the browser only when it is not (a declared or undeclared
divergence, a board left on an older template) or when the template changed since
`verify/verify-templates.js` verified it.

## 2. The four columns

One row per part of the change a reader could point at: a class or file, a test suite, a
living document, a build file, a release step — and, under the group **Left for later**, a
scope item the plan deliberately leaves alone, so the decision not to act is on the board with
its reason. Groups order the board: `Code`, `Tests`, `Documents`, `Release`, `Left for later`.
On a tracking issue's board the rows are its units. Four to twelve rows is usual.

| | Column | Holds | Written |
|---|---|---|---|
| 1 | **Gap** | what was wrong or missing at the baseline, with evidence (`path:line`) and a source in the research | once, after research; for a sub-issue of a signed-off tracking plan, at `sized`, from the parent's research and architecture (its unit row in the decomposition, the current-state section) |
| 2 | **Considered** | every option weighed, each with a verdict: **accepted** (green), **declined** (red, with the trade-off that ruled it out), **partial** (yellow: adopted in part, with what was taken and what wasn't), **deferred** (yellow until settled: left open at plan time, settled in column 4). Exactly one option per row is accepted or partial-as-chosen. | once, after architecture; for a sub-issue of a signed-off tracking plan, at `sized`, the options the parent's architecture weighed for this unit (its alternatives-considered and per-unit design sections), to which the unit's own plan adds at `plan-accepted` |
| 3 | **Verdict** | the decision and its defence in a few sentences (what the work is — one system, a bug fix, docs only — never its work level); a `build` or `leave` kind (a neutral, solid chip, "build" or "leave as is", which the Timeline legend names: a decision, not an outcome, and never dashed, `GUIDANCE.md` §1); the steps named, not listed (a step is a sentence with a file anchor and its check — the detail is in `plan.md`); tests by test level; risks | once, at plan acceptance |
| 4 | **As built** | the state, a summary of what exists at the as-built commit, and every change from the verdict with `what`, `why`, `when` (the stage or review round) and `ref` (the commit) | kept as the work lands |

Columns 1–3 are written once. A factual error found later is corrected in place and noted
under `notes.corrections`; a change of mind goes in column 4, never into column 3.

**As-built states:** `pending` (dashed, neutral) · `as-planned` (green) · `amended` (yellow:
built as decided, plus changes added in implementation or review) · `deviated` (orange: the
decision itself changed; each difference and the new decision listed) · `dropped` (red, with
the reason) · `deferred` (neutral, dashed, with the issue it went to). A tracking board's
**unit rows**, and only they, take two more: `complete` (green, outlined: implemented and qa
passed, not merged yet; the pipeline's `qa-pass` event sets it) and `landed` (green: merged; the
admin team sets it itself in the landing refresh, with no plan-board event from a pipeline). An
issue board's rows never take them: they keep `as-planned`, `amended` or `deviated`.

On a tracking board a unit row moves `pending` → `complete` → `landed`: `complete` when its
sub-issue's run passes qa, `landed` when that sub-issue merges. The detail of what the unit built,
and how it differs from its own verdict, stays on the sub-issue's board, which the row links; the
row may still carry `changes[]` where the unit departed from the architecture. A tracking board
written before these two states marked a landed unit `as-planned`, `amended` or `deviated`; the
scripts and the page read those as landed.

**The As built tile** in the header counts what is **built**: "N / M rows built", N the rows
`as-planned`, `amended` or `deviated`, M every row less the `dropped` and `deferred` ones, which are
neither built here nor counted in the total, as the chain's progress counts them (§3). The line under
the figure names every state with its count, dropped and deferred included. A tracking board's tile
reads "N / M units landed", counted the same way.

### Impact

Beside the four columns, a core tab, **Impact**, says what the change means outside itself, from
`plan.json` `impact`. It is a general representation like the rest of the board: summaries and
links to the Markdown section that holds the detail, never listings.

| Section | Holds | Each entry |
|---|---|---|
| **Downstream effects** | who or what downstream is affected: consumers, other systems and repositories, published artifacts, operators | `who`, `kind` (`consumer` · `system` · `repository` · `artifact` · `operator`), `effect` (`none` · `additive` · `behaviour` · `breaking`), `summary`, `system`, `link` |
| **Adaptation requirements** | what a consumer or another system must change to adopt it | `who`, `need` (`none` · `optional` · `required`), `summary`, `system`, `link` |
| **API changes** | public surface added, changed, deprecated or removed, with its stability tier where known | `surface`, `change` (`added` · `changed` · `deprecated` · `removed`), `tier` (`stable-core` · `supported-extension` · `experimental` · `internal`, or `null` when not stated), `summary`, `system`, `link` |
| **Conversion steps** | the ordered migration steps a consumer follows | `what`, `link` |

Around them: `basis` (`plan` until the impact is reconciled, `as-built` once it is: two values,
and never a third), a `summary` of two to four lines, `release`
(`bump`: `none` · `fix` · `feat` · `major`, the `version`, an optional `note`), `none` (a plain
statement of why no downstream impact is recorded, or `null`), `changes[]` (each difference from
the planned impact, as column 4 records them: `what`, `why`, `when`, `ref`, and optionally `entry`,
the entry it changed as `<section>.<index>` such as `api.0`, and `system`; on a tracking board also
`unit`, the unit row id whose landing recorded it, and a unit's **no change** entry, below), `source`
and `link`. An entry's `system` is a registry slug from `systems`, or `null` for a party outside the
repository's systems. `basis` is data for the reconciliation and the checks, and the Impact tab
renders neither it nor `changes[]` (`GUIDANCE.md` §1, no planning information on the Impact tab):
**the As built tab shows `changes[]`** (below, "How the impact differed from the plan").

**The reconciliation state is derived, never stored.** From the data already on the board, by one
rule: **`planned`** — `basis` `plan`, no `impact.changes` entry recorded and, on a tracking board, no
unit landed; **`partial`** (*partly reconciled*) — `basis` `plan`, with an `impact.changes` entry
recorded or a unit landed (on a tracking board, n of M units landed, counted as the chain's progress
counts them, §3); **`as-built`** — `basis` `as-built`. A board with no impact recorded (`impact`
`null`) has no state. The rule is written once per runtime, so it cannot drift: `plan/scripts/lib.js`
`reconciliation()`, which `check.js` and `board.js` use, and the template's `reconciliationOf()`. The
page shows the state as a chip on the As built tab (below) and the work board shows it on each row
(§5); the Impact tab never does.

Every entry, a unit's included, may carry `compat` (`compatible` · `notable` · `breaking`), its
compatibility. It is derived from the entry and the field only **raises** it: a `breaking` effect
and a `removed` surface are breaking; a `behaviour` effect, a `deprecated` or `changed` surface and
a `required` adaptation are notable (worth noting); everything else is compatible. The presenter
sets `compat: "breaking"` on a required adaptation that breaks a consumer that does not make it (or
a changed surface that breaks), and `compat: "notable"` on an entry worth noting that its fields do
not show, such as a lettered or strict-version requirement; a conversion step or a unit entry takes
`compat` alone.

- **Sources.** The issue folder's `impact.md`, which the planner writes while planning and
  reconciles once implementation ends; `plan.md` where it states API or migration facts; and
  `final-implementation.md` for the as-built impact.
- **When.** `new.js` sets `impact` to `null`. The `plan-accepted` event writes it from
  `impact.md` and `plan.md`, with `basis` `plan`. From then on its `changes[]` **accumulate as the
  work lands** while `basis` stays `plan`: the impact is *partly reconciled* (the derived state
  `partial`). A deviation in
  `final-implementation.md` that changes the impact goes into `changes[]` at its
  `implementation-stage` event, naming the `entry` it changed, and that entry shows the current
  best-known impact; on a tracking board, each unit's landing adds what it changed in the
  initiative's impact (below, "Tracking boards"). The `landed` event — on a tracking board, the
  last unit's — reconciles the rest of the sections from `final-implementation.md` and the
  reconciled `impact.md`, sets `basis` `as-built`, and keeps every difference from the planned
  impact in `changes[]`: the planned impact is never silently rewritten.
- **The look: compatibility first** (`GUIDANCE.md` §1, the Impact tab's exception). A **breaking**
  entry is a **red** card, a **notable** one a **yellow** card, and a compatible one a card in its
  system's colour (muted for a party outside the repository's systems). A red or yellow card names
  its system in a badge, and carries a `✕ breaking` or `⚠ worth noting` pill where none of its
  badges already says it. The effect, need and API-change badges take the same colours (`!
  breaking`, `✕ removed` red; `~ behaviour change`, `⚠ deprecated`, `~ changed`, a required change
  that does not break, yellow; a required change that breaks, red); kinds and tiers stay neutral.
  The tab's legend lists exactly what it drew.
- **No planning information** (`GUIDANCE.md` §1). The tab shows only the current best-known impact:
  every entry is the same **solid** card, whether the impact is still the plan's or reconciled; no
  pill tells the planned impact from the as-built one; no list of changes from the planned impact;
  nothing on the tab is dashed (the no-impact statement and an empty section included). How the
  build differs from the plan is told on the As built tab: the rows' `changes[]`, and the impact's.
- **How the impact differed from the plan: on the As built tab.** Under the row cards, a section
  **Impact changes from the plan** shows `impact.changes`, one card per difference: its `what` as
  the title, its `why`, its `when` and `ref`, and, where it names an `entry`, a link that opens that
  entry's card on the Impact tab, selected (`#impact.<entry>` deep-links it). A card takes its
  system's colour — its own `system`, else its entry's, muted for the impact as a whole or a party
  outside the repository's systems — and is solid; no status colour (a change from the planned
  impact is a record, not an outcome) and never the Impact tab's compatibility red or yellow, which
  belong to that tab alone. On a tracking board the initiative's changes come first, then each
  unit's own (`impact.units[].changes`) under the unit's number and title (the pair of §1), linking
  its unit card on the Impact tab; units reconciled with no change are named in one line. Over the
  cards stands the **reconciliation chip**, the derived state (above) with its glyph and word in the
  colour coding of `GUIDANCE.md` §1 — `… planned` neutral and dashed, `◐ partly reconciled` yellow
  (on a tracking board "partly reconciled · 2 of 11 units"), `✓ as built` green — beside one line
  saying how far the reconciliation has got: "Nothing reconciled yet", "So far, with 2 of 11 units
  landed", on an issue board "So far, as implementation recorded them", or "Reconciled with the
  build". The section is drawn in all three states once the board records an impact. Once the impact
  is reconciled with no difference it says "None". On a tracking board, the units that recorded a
  **no change** entry are named in one line ("None so far: …" while nothing else changed the
  initiative's impact and every landed unit has its record); "None so far" is said only from those
  recorded entries, never inferred from absence, and a landed unit with no entry is named on a dashed
  line, "Not recorded yet". The tab's legend lists the system swatches and the muted bar it drew, the
  chip it drew, and the dashed line when it drew one.
- **No recorded impact** (common for a small bug fix) is never a hidden tab: the tab states
  plainly "No downstream impact recorded" with the `none` statement and its source; before plan
  acceptance it says nothing is recorded yet and where it will come from. A change with no
  downstream effect moves no version (`release.bump` `none`), and the tab says so explicitly.
- **Tracking boards** show the initiative's own impact, from the tracking issue's `impact.md`,
  then a **Units** section: one card per unit row, from `impact.units[]` (`unit`: the row id,
  `basis`, `summary`, `release`, `source`, `link`, and `changes[]`, the unit's own differences from
  its planned impact, written when its entry is reconciled and shown on the As built tab), summarising that unit's own impact and linking
  its board by the number-and-title rule (§1). A unit with no entry shows "not recorded yet",
  in the same solid card. The presenter writes a unit's entry at its sub-issue's `plan-accepted` event (basis
  `plan`) and reconciles it in its landing refresh (basis `as-built`, each difference from the unit's
  planned impact in its `changes[]`), from the sub-issue's own board and `impact.md`. The initiative's `release.bump` is `none`: a tracking plan moves no
  version itself, and each unit's release is its own.
- **The initiative's impact accumulates as its units land, and every landed unit records its
  effect.** In each unit's landing refresh the presenter adds to the tracking board's
  `impact.changes` that unit's effect on the initiative's own impact (from the sub-issue's board and
  `final-implementation.md`, and the tracking issue's `impact.md` where the planner has reconciled
  it): every difference its landing makes, each naming the unit in `unit` (the row id) and in its
  `when` ("#62 landing") and the `entry` it changed, and that entry shows the current best-known
  impact; or, when its landing changed nothing in the initiative's impact, one explicit **no
  change** entry, `{"unit": "build-logic", "when": "#61 landing", "none": true}` (optionally a `why`
  and a `ref`; never an `entry`, and only on a tracking board). Every landed unit has one or the
  other: an absence is never read as "no change". `basis` stays `plan`, partly reconciled, until the last unit lands; that
  landing reconciles the initiative's impact whole and sets `basis` `as-built`. A unit's own entry
  in `impact.units` has no such phase: it moves from `plan` to `as-built` in its unit's landing
  refresh, all at once.

### The tabs

The board's tabs are **Timeline** (the four columns), **Decisions**, **As built** (column 4's
cards, then how the impact differed from the plan, §2), **Impact** and **Source**; a tracking board adds **Landing Order**. On the Timeline the four phase columns read as
columns: each stands on its own neutral band under a strong, sticky head (its number, its name, its
question, its milestone). The bands are layout, not an encoding: they take no colour of their own,
so system and status colours keep their meanings, and the legend does not list them; the narrow
layout stacks each row and draws none. A tab's lede is at most one short line, and only for what its
graphic and legend do not show (`GUIDANCE.md` §2); the work board's Runs lede too.

**Landing Order** (tracking boards) draws the units as a dependency graph in landing order: a column
is the earliest a unit can start, an arrow runs from a unit to the units it blocks. The graph spans
the full width of the content area, and the inspector sits **under it** on this tab, its sections as
bubbles left to right in the inspector's own order (what was selected first, then one bubble per
sub-heading; short ones at the end stacked in one column), wrapping on narrower screens and in one
column on a phone. Every other tab keeps the inspector beside it. The tab was called Chain; a link to
`#chain` still opens it.

## 3. Work in progress

A board is alive while its run is. Its data carries:

- `wip.step` — the pipeline step the run is at (`sizing`, `interview`, `research`,
  `architecture`, `plan`, `branch`, `implementation`, `qa`, `remediation`, `landing`,
  `landed`, `halted`, `escalated`, `cancelled`), with `since` (date-time) and `detail` (one
  line: which stage, which qa pass, what waits on the user); on a tracking board it is the
  tracking issue's own phase (below, "The units' own runs");
- `wip.current` — the cells being worked on, as `<row-id>.<column>` addresses, or a column
  name while a column is being written; these carry the **in-progress mark**, the breathing
  interior glow (`GUIDANCE.md` §1). `wip.current` means a run is actively in progress and
  nothing else. What it holds **follows `wip.step`**, by the step-to-column map below: during
  research the Considered cells of the rows being researched; while a plan is written or verified, Considered and Verdict;
  during implementation the As built cells of the rows the current stage touches; during qa the
  whole As built column lightly; while halted, the glow of the step it halted in holds still as a
  ring, and a yellow "waiting on the user" strip says for what;
- `wip.next` — on a tracking board only: the id of the **next unit in landing order** — the
  first unit row, in the board's row order, that is `pending` and not in `wip.current` — or
  `null` when none is left. A tracking board always names what is coming. It carries the **up-next mark**, the still, mild
  outer glow and the UP NEXT tag (`GUIDANCE.md` §1), on the unit's as-built cell, its chain
  entry, its card and its roadmap line; it never glows as in progress, and the work board shows
  it as "next · not started", never building or active. If the unit's blockers
  (`unit.blockedBy`) have not all landed, it is still named next and is tagged "blocked by #n"
  for each one that has not (a blocker that is not a unit on the board counts as not landed on
  the plan board; the work board also reads the tracker's *blocked by* links, and takes a
  blocker with no board as landed once its issue is closed). A unit is never in `wip.next` and
  `wip.current` at once;
- `wip.questions` — the run's research questions while it researches, each `{question, rows,
  findings}`: the question's slug, the ids of the rows it concerns (`[]` when it names none), and
  `findings`, `null` while the question is open and its findings file once it has returned. The
  `research-started` event adds questions, `research-returned` closes one, `researched` clears the
  list (the trail keeps each findings file); from it the research glow is computed (below);
- `wip.qa` — passes so far, each with its verdict and finding counts;
- `wip.blockers` — issues this run waits on, and runs waiting on it (from *blocked by* links).

**The glow follows the step: the step-to-column map.** Every `wip.step` gives `wip.current`
one shape, on an issue board, a sub-issue's board and a tracking board alike; the presenter sets
`wip.current` from it at every event that moves the step, and during research at every event that opens or closes a question (§4), and `check.js` warns on a board
that does not keep it (§8). The map is written once for the scripts, as `GLOW_MAP` in
`plan/scripts/lib.js`, which `check.js` and `new.js` use.

| `wip.step` | `wip.current` — what glows |
|---|---|
| `sizing` | nothing: the board is laid at `sized`, which moves the step on |
| `interview` | the cell the question concerns, as `<row-id>.<column>`, or nothing; never a whole column |
| `research` | the Considered cells of the rows being researched, `<row-id>.considered` (below, "Research: the rows being researched"); the whole Considered column, `considered`, as the fallback |
| `architecture` | `considered`: the architecture weighs the options (a tracking board's units appear at its sign-off) |
| `plan` | `considered` and `verdict`, both while the plan is written and while an existing plan is verified (a planner re-pass over a plan already written, which runs at this step) |
| `branch` | nothing: the Verdict is written and the build has not started |
| `implementation` | the As built cells of the rows the current stage touches, as `<row-id>.built`, at least one; on a tracking board, the As built cells of its units in progress (`<unit-id>.built`), or nothing between a unit's landing and the next unit's start |
| `qa` | `built`: the whole As built column, lightly |
| `remediation` | the As built cells of the rows the qa findings touch, as `<row-id>.built`, at least one |
| `landing` | nothing: qa has approved and the merge is the admin team's (on a tracking board, its plan's own landing) |
| `landed`, `cancelled` | nothing: the glow is off |
| `halted` | the glow of the step it halted in (`wip.resume`), unchanged, drawn as a still ring |
| `escalated` | the glow of the step it escalated from (`wip.resume`), unchanged, drawn as a still ring: the run waits on the user's re-sizing, as a halt does |

**Research: the rows being researched.** During `research`, `wip.current` is the union of the
`<row-id>.considered` cells of the rows the **open** questions in `wip.questions` name: a
`research-started` event lights its questions' rows, and a `research-returned` event puts out the
rows of the question that returned, except a row another still-open question names, which keeps
glowing. Once every question has returned, the **verification** runs (until `researched`), and the
Considered cells of every question's rows glow again. That is the default, pending the user's
answer; the alternative is the whole Considered column during the verification, switched by
`RESEARCH_VERIFY_GLOW` in `plan/scripts/lib.js` (`"rows"`, the default, or `"column"`) and this
paragraph together. **The fallback** is the whole Considered column, `considered`: while no
question is recorded yet (a board laid at `sized` with the step at `research`), when a question
in the set names no row (`rows: []`, or only ids that are not rows of the board), when the board
has no rows, and when the cells would be more than six (the glow cap). A halt during research
keeps that glow, held still. The rule is written once, `researchGlow()` in `plan/scripts/lib.js`,
which `check.js` applies; the page draws whatever `wip.current` names.

A tracking board's own steps are its phase (below, "The units' own runs"), and the map reads
them the same way; each unit in progress glows on its own board by its own run's step, and on
the tracking board only as its unit's As built cell.

The page shows this as a **WIP strip** under the header: the step as a progress line through
the pipeline's steps, the detail, the qa passes, the blockers, and the last update time; on a
tracking board also the chain of units, the unit in progress and the unit up next. When the
change lands, `status` becomes `built`, `wip.step` becomes `landed`, the glow stops, and the
strip shows the landing (PR, merge commit, version).

**A tracking board's strip is a set of bubbles** once it has units: (1) the tracking issue's own
phase — its step, steps line and detail — with the chain's progress (landed of all, complete, the
thin green bar) and the chain of units, its blockers and its landing; (2) one bubble per unit in
progress, with its own run (below): the run pill, its own steps line, its detail, since and
updated, its qa passes and its branch; (3) the unit up next, with its UP NEXT tag and a "blocked
by #n" tag for each blocker that has not landed; (4) **waiting on you**, a yellow bubble shown only
while the tracking issue or a unit's run is halted, saying what each waits on and where it resumes.
On a phone they stack in that order; up to 1500 px the phase runs across the row with the others
beside each other under it; on a wide desktop the phase takes two columns and the others sit beside
it. An issue's number and its title in a bubble are the pair of §1. The legend runs under them all.
An issue board keeps its single strip: one run, nothing to separate.

**Branches.** A merged branch is not shown. An issue board names its branch (the header chip)
until it has landed. A tracking board names its own branch, the one its plan was written on, only
while that plan is in flight; once the plan has landed — the board's `wip.step` (or the step a halt
or escalation resumes at) is past `landing`, its `status` is `building` or `built`, `wip.landing`
records the plan's merge, or a unit has started — no header, strip or work-board row shows it. A
unit's branch shows while its run is live (its mirror's `branch`, `unit.branch`) and stops once the
unit has landed. The page and `board.js` derive this from the data; nobody clears a branch by hand,
and the trail keeps every branch's history.

**The units' own runs (tracking boards).** A tracking board reflects the live state of every
unit in progress. Two things say where the work is, and they never mix:

- **The tracking board's own `wip`** is the tracking issue's phase, never a unit's step. Its
  steps are `sizing`, `interview`, `research`, `architecture`, `landing` (the plan's own landing)
  and then `implementation`, which spans its units' runs from the first unit's start until the
  last unit lands, then `landed`. While any unit runs, `wip.step` stays `implementation`, whatever
  step each unit is at; `halted`, `escalated` and `cancelled` mean the tracking issue itself (an
  architecture re-pass, the whole chain stopped), never one unit's halt. `wip.detail` speaks for
  the chain (which unit landed, which runs, which is next) and is written at the chain's own
  moments: a unit's start, its approving qa pass, its landing. `wip.qa` stays empty: qa passes
  belong to the units.
- **Each unit in progress mirrors its own run**, as `unit.live` on its row: its sub-issue board's
  `wip` as the pipeline last left it — `step`, `since`, `updated`, `detail`, `steps`, `waitingOn`,
  `resume`, `qa`, `qaMax`, and `proposedLevel` while escalated — plus that board's `status` and
  `branch`. Nobody writes it by hand. `embed.js` writes it at every embed of the tracking board,
  from the `plan.json` of the unit's board in the same tree (the unit's folder inside the tracking
  folder, §1), for every unit in `wip.current` while the tracking board is live; and every embed of
  a sub-issue's board re-embeds its parent's tracking board in the enclosing folder, so every event
  of the unit's run reaches the tracking board, not only `sized`. A unit that is not in progress,
  that has no board in the tree, or a tracking board that has landed or was cancelled carries no
  mirror; `embed.js` clears one that is left. The mirror is generated, never merged: where two
  branches changed it, take either side and re-embed.

The page shows the mirror wherever it shows the unit in progress: on the WIP strip, in the unit's
own bubble with an accent edge, its step, its own steps line, its detail and its qa passes (a
yellow edge, and its question in the "waiting on you" bubble, while its run is halted); in the
unit's as-built cell and its card on the As built tab, as a run line (`▶ run at <step>`, or
`⏸ waiting on the user` with the step it resumes at, its latest qa pass, and when the board was
updated); in the inspector's unit entry, in full; on its chain node, in place of its state; and in the Context roadmap. While a unit's run waits on the user its in-progress mark
pauses to the ring alone, as the whole board's does while the tracking issue itself is halted
(`GUIDANCE.md` §1). The tracking strip's bubbles run in that order: the tracking issue's own phase
with the chain, each unit in progress with its run, the unit up next, then waiting on you.

**The chain's progress (tracking boards).** A tracking board's `status` stays `building` from its
first unit's start to its last unit's landing, so its header does not show it. In place of the
status chip it shows the chain's progress, with a thin green bar of units landed:

> chain **1 of 11 landed** · #47 in progress (plan) · #62 up next, blocked by #47

- **Landed count:** units landed of all units. Units `dropped` or `deferred` are left out of the
  total and named after it ("· 1 dropped"). A unit written as `as-planned`, `amended` or
  `deviated` before the `landed` state existed counts as landed.
- **In progress:** each unit in `wip.current`, with its own run's step from its mirror
  (`unit.live`), so the chip follows every event of the unit's run. A unit whose run is halted
  reads "#47 waiting on you"; an escalated one "#47 escalated"; one with no mirror yet "#47 in
  progress".
- **Up next:** `wip.next`'s issue, with "blocked by #n" for each blocker that has not landed.
- **Before any unit starts** (none landed, complete or in progress): "planned · 11 units". **All
  landed** (or the board built): "landed · 11 of 11". A cancelled tracking issue: "cancelled · n
  of M landed".
- Every `#n` here is a lone `#n` (§1): it opens the issue's board when one exists.

An issue board keeps its status chip unchanged. On the work board, a tracking issue's state cell
shows the same summary in place of a bare "building" (§5).

**Next is the next one up (the standing rule).** `wip.next` is always the next unit in
landing order, and two moments move it:

- **A sub-issue lands.** The landing refresh, with no event and no request, updates its
  tracking board: the unit's as-built cell becomes `landed` (with the as-built summary of the
  landing), the unit leaves `wip.current`, and `wip.next` is recomputed.
- **A unit's run starts** (its first plan-board event, `sized`). On the tracking board the unit
  moves from `wip.next` to `wip.current` (`<unit-id>.built`), and the **following** unit in
  landing order becomes `wip.next` at once; the tracking board's `wip.step` is `implementation`
  from the first unit's start, and the unit starts mirroring its run (above).

Recomputing always means the same thing: the first unit row, in row order, that is `pending`
and not in `wip.current` (so never one that is current, complete, landed, dropped or deferred),
or `null` when there is none. A unit is never in `wip.next` and `wip.current` at once.

## 4. Events: what updates a board

The pipeline never edits a board. At every step transition it sends the admin team a
`plan-board` request naming the event; the presenter reads the issue folder's documents and the
event's facts, updates `plan.json`, re-embeds, checks, and the team commits the folder on the
issue's branch, so the board's git history is the run's own timeline.

**Every event of a sub-issue's run reaches its tracking board.** Re-embedding the sub-issue's
board (`embed.js <folder>`, which every event ends with) re-embeds the parent's tracking board in
the enclosing folder, which mirrors the unit's run from the `plan.json` just written (§3). So on
every event below, for a sub-issue, the tracking board changes too: at least `unit.live`, and on
`sized`, an approving `qa-pass` and `landed`, the unit's row and `wip` as the table says. On
`sized`, move the unit into the tracking board's `wip.current` before the last embed, or the
mirror starts at the next one. The presenter checks both boards.

| Event | When | What the presenter writes |
|-------|------|---------------------------|
| `sized` | step 1 done (levels 2–4) | the **foundation**: `new.js`; issue, title, level (data only, never shown), baseline, systems, status `planned`, `wip.step = interview`/`research`/`plan`, and `wip.current` from that step's row of the map (§3): nothing or the cell the interview's question concerns, `considered` for research (the whole column, until `research-started` names its questions), `considered` and `verdict` for a plan (`new.js` lays the columns; a cell is the presenter's to name); milestones empty; on the work board. For a sub-issue of a tracking issue whose parent board has passed `architecture-signed-off`, the Gap and Considered columns are filled at once from the parent's documents, with the `gap` and `considered` milestones: the gap from the parent's research README and architecture (the unit's row in the decomposition, the current-state section it rests on), the options from the alternatives the architecture weighed for this unit and the design decisions of its section, each with the verdict the architecture gave; a board of such a sub-issue is never born with empty columns, since its research and architecture happened in the parent's run. Also on the tracking board: its unit moves from `wip.next` to `wip.current` (`<unit-id>.built`), the following unit in landing order becomes `wip.next`, and `wip.step` is `implementation` (§3); `new.js --parent` embeds the new board, whose "part of" chip then opens the tracking board, and `embed.js` re-embeds the tracking board, which links the unit to the new board (§1) and, once the unit is in `wip.current`, mirrors its run (§3) |
| `halted` / `resumed` | a planner halt, a qa stop, a `needs-user` | `wip.step = halted` with what waits on the user, and `wip.resume` the step it halted in; `wip.current` stays as that step left it, and the page holds its glow still as a ring (§3); on resume, back to the step, with the glow that step's row of the map gives (a resumed plan verification: `considered` and `verdict`). For a sub-issue, its tracking board's `wip.step` does not change: the unit's mirror carries the halt, and its mark pauses (§3) |
| `research-started` | the planner sends its research questions out (`facts.researching: [{question, rows}]`) | each question appended to `wip.questions` with `findings: null` (and `started`, the event's time); `wip.step = research`; `wip.current` the union of the `<row-id>.considered` cells of every open question's rows, or the whole Considered column by the fallback (§3, "Research: the rows being researched") |
| `research-returned` | a researcher returns (`facts.returned: {question, findings}`) | that question's `findings` set to the findings path (and `returned`, the event's time); a trail entry for the findings (`column` `gap`, a label naming the question, `ref` the findings path); `wip.current` recomputed: the question's rows stop glowing unless another open question names them, and once every question has returned the verification glows every question's rows again (§3) |
| `researched` | research verified | the Gap column from `research/README.md` and the findings; the `gap` milestone; `wip.questions` cleared (research has ended; the trail keeps the findings); `wip.step` the step the event's facts name next (`architecture` on a tracking issue, else `plan`) and `wip.current` from the map: `considered`, or `considered` and `verdict` (§3) |
| `architecture-signed-off` | level 4 sign-off | the Considered column from `architecture.md`; on a tracking board, the unit rows (each `pending` with a one-line progress summary until its sub-issue lands; `embed.js` links it to the sub-issue's board once that board exists, §1), and `wip.next` the first unit (§3); `wip.step = landing` (the plan's own landing) and `wip.current` empty |
| `plan-accepted` | planner COMPLETE | Considered (if not yet) and Verdict from `plan.md`; the `verdict` milestone; `impact` from `impact.md` (and `plan.md` where it states API or migration facts), `basis` `plan` (§2, Impact); `wip.step = branch` and `wip.current` empty (§3: nothing glows between the Verdict and the build). For a sub-issue, its unit's `impact.units` entry on the tracking board |
| `branch-cut` | step 3 done | the branch; `wip.step = implementation`; `wip.current` the As built cells of the rows the first stage of `plan.md` touches (`<row-id>.built`) |
| `implementation-stage` | a rookie-dev stage or report | `status = building`; the touched rows' as-built state and summary; each deviation from `final-implementation.md` as a `changes[]` entry, and one that changes the impact added to `impact.changes` with the entry it changed (`basis` stays `plan`: partly reconciled, §2, Impact); `wip.current` = the As built cells of the rows the next stage touches (`<row-id>.built`); once the last stage is reported and the run moves to qa, `wip.step = qa` and `wip.current` `built` (§3) |
| `qa-pass` | a qa verdict | `wip.qa` appended; `wip.step = remediation`, with `wip.current` the As built cells of the rows the findings touch, or `landing`, with `wip.current` empty (§3). On an approving pass of a sub-issue's run, its unit row on the tracking board becomes `complete` (it stays in `wip.current` until it lands) |
| `escalated` | a level escalation | `wip.step = escalated`, `wip.resume` the step it escalated from, and `wip.current` unchanged, its glow held still as a ring (§3); the proposed level is kept as data only (`wip.proposedLevel`, never shown: `GUIDANCE.md` §4); the board follows the issue's new sizing |
| `landed` | the team has merged | never sent by a pipeline: the admin team raises it itself inside the landing refresh (the presenter writes, the executor commits). On the issue's board: `status = built`; `asBuilt` (sha, date, PR, merge, version); the `built` milestone; every `pending` part resolved; the trail completed; `impact` reconciled from `final-implementation.md` and the reconciled `impact.md`, `basis` `as-built`, each difference from the planned impact in `impact.changes`, naming the `entry` it changed where there is one (§2, Impact; the As built tab shows them); `wip.step = landed` and `wip.current` empty. For a sub-issue, on its tracking board, the standing rule (§3): the unit `landed`, out of `wip.current` (which clears its mirror at the next embed), `wip.next` recomputed as the next unit in landing order; its `impact.units` entry reconciled, `basis` `as-built`, each difference from the unit's planned impact in its `changes[]`; its effect on the initiative's impact recorded in the tracking board's `impact.changes`, always: each difference its landing makes, with `unit` set to the unit's row id, or one no-change entry `{unit, when, none: true}` when it changed nothing; that `basis` stays `plan` until the last unit lands and becomes `as-built` with it (§2, Impact). Then the work board is regenerated |
| `cancelled` | the run is abandoned | `status = abandoned`, reason in `notes`; `wip.step = cancelled` and `wip.current` empty |

The **work board** (§5) is regenerated only at landings, as part of the landing refresh, and
committed with it; between landings it may lag, and a run's live state is on its own board, on
its branch. After `landed`, the as-built system pages' Context links are refreshed too.

## 5. The work board

`docs/plans/index.html`, from `board.json`, generated by `board.js` from every `plan.json`
under `docs/plans/` plus the tracker's open issues (`gh issue list`, sub-issues, *blocked by*):
one row per issue that has a board or a `level:` label (the label only decides which issues are
rows; no level is written to `board.json` or shown), and one per unit of a tracking board —
its status, `wip.step` and detail, qa passes, what it waits on, its blockers and what it
blocks, its branch (never a merged one, §3), and its tracking parent; grouped by tracking issue in landing order, then the
rest by age; the in-progress mark on the rows whose runs are active; the same system colours. A
unit reads `complete` once its row is complete (qa passed, not merged) and `landed` once it has
landed; a tracking issue's own row shows its chain's progress (§3) in its state cell, from
`chain` in `board.json` (`total`, `landed`, `dropped`, `deferred`, `planned`, `done`, `current[]`
with each unit's step from its freshest board, else the mirror, and `next` with its open
blockers), instead of a bare "building", keeping its pill above it only while the tracking issue
itself is halted, escalated or cancelled; the unit a tracking board names in `wip.next` reads
"next · not started", with the
up-next mark and a "blocked by #n" tag for each blocker that has not landed, and is never active. A
row with a board of its own carries its impact's reconciliation state (§2, Impact) as
`reconciliation` in `board.json` — `{state, landed, total}`, `state` `planned` · `partial` ·
`as-built`, `landed` and `total` the units landed of all on a tracking issue's row and `null` on an
issue's, the whole field `null` while the board records no impact or the row has no board — which
`board.js` derives through `lib.js` `reconciliation()`, never by hand; the state cell shows it as a
chip under the state ("impact partly reconciled · 1 of 11"), in the same colours as the board's
chip, with its legend entry. Its Context lists the roadmap
(tracking issues) and the unscheduled issues, like the repository page, and links it. Its links follow §1: in each row, each
group heading, each roadmap item and each unscheduled issue the number opens the GitHub issue and the title opens the issue's
board, a tracking issue's as much as a sub-issue's (plain text while it has none); a lone `#n` — the "part of" line of a unit, the
waits-on and blocks lists, the "blocked by" tags, the Up next count, any `#n` in the text — opens the board when one exists and
GitHub otherwise. There is no separate GitHub ↗ link: every issue with a board has a row whose number opens GitHub. `board.js`
sets a row's board only when its file exists.

**A row's system, and "no system".** A row's `system` for an issue with no board, and an unscheduled
issue's `system`, are the presenter's: recorded once in `board.json`, and kept by `board.js` from the
previous board (the one it writes, then the other of the committed and the live board). Where the user
has decided that an entry belongs to no system (a docs-only issue that changes only a planning record,
say), the entry records `"unassigned": true` with `system` `null`, the record of that decision:
`board.js` keeps it, the row reads "no system" with the muted swatch, and the entry is no longer
reported as missing a system. An entry with neither is reported at every `board.js` run until one is recorded.

## 6. Who does what

| Who | Does |
|-----|------|
| the `/resolve-issue` pipeline | sends `plan-board` events with the facts it has (step, verdicts, counts, documents written, what waits on the user); never edits a board |
| the planner, implementer, qa | write their Markdown as before; the board is read from it |
| the presenter (admin team service) | writes `plan.json`, re-embeds, checks, fills `board.json`; decides the rows and the summaries from the documents; sets `wip` from the event; on a sub-issue's event, re-embeds and checks its tracking board too, whose units' runs `embed.js` mirrors (§3; the presenter never writes `unit.live` by hand); in a landing refresh, sets the landed state and applies the standing rule (§3) on the tracking board |
| the admin team's executor | commits the folder on the issue's branch after each event, with its tracking board's `plan.json` and `dashboard.html` when a sub-issue's event changed them (a mirror conflict between branches is resolved by re-embedding, §3); commits the regenerated work board only in a landing's docs flow |

## 7. Writing

Sentences, not fragments; present tense in columns 1–3, past tense in column 4; file paths and
identifiers in `` `code` `` spans and issues as `#n` (the page links both); a cell's summary
stands alone in two to four lines, and the detail link goes to the Markdown section that holds
the rest. No code listings. Numbers only where they decide something. Never a work level
(`GUIDANCE.md` §4): no "level 3", "L3" or "a level-3 change" anywhere on a board; say what the
work is (one system, a bug fix, docs only). The rule is about work levels only: a test level keeps
its level label ("Level 2 — component", "L1 gating", "L4a deterministic"), and so does a C4 level.

## 8. What `check.js` enforces

Fails: schema/repo/issue/slug/title/function/baseline/status missing or bad; a slug that is not
the folder name or doesn't start with the issue number; a `built` plan with a `pending` part or
without `asBuilt.sha` and `.date`; a `planned` plan with a non-pending part; a row without id,
name, system or gap summary; a row without options once the `considered` milestone exists, or
without a verdict summary once the `verdict` milestone exists (a board between research and
plan acceptance carries the Gap column alone); options without exactly one accepted (or
chosen-partial) verdict; a declined, partial or deferred option without `why`; an amended or
deviated part without `changes[]`, or a change without `what` and `why`; a dropped part
without a reason; a deferred part without an issue; a `wip.current` address that names no cell; a `wip.questions` that is not an array of `{question,
rows, findings}` (a kebab-case slug, row ids, `null` or a path), or names a question twice;
more than six glowing cells; `complete` or `landed` on a row that is not a tracking board's
unit row; a `wip.next` on a board that is not a tracking board, or one that names no unit row,
a unit that is not `pending`, or a unit also in `wip.current`; on a tracking board, a recorded
`wip.next` (`null` included) that is not the next unit in landing order (§3); a landed unit
still in `wip.current`; a tracking-board unit row whose sub-issue's board exists in this tree
but is not what its `unit.board` links, or a `unit.board` naming a board that does not exist; a

excepted), an impact change
whose `entry` is not `<section>.<index>` or names no entry (the As built tab would link a card
that is not there), a unit entry's change that names an `entry`, an impact change's `unit` on an

(`GUIDANCE.md` §1: a `--sys-N` slot, chromatic, with a hue outside 175°–295°, read from the page's

With `--auto` it reports the page's standing against its template (`system/scripts/deviation.js`):

(§1) — a unit, the parent or any other issue the board names — one warning per issue, naming
each place and the fix: a page on a template older than the rule (re-render it), a `unit.board`,
`parent.board` or `issueBoards` entry not re-embedded (run `embed.js`), or a GitHub URL of the
issue written in the data; on a page older than the rule, the issue references it leaves as
plain text for issues with no board; the same on the work board; an `issueBoards` entry that
`embed.js` would no longer write; a sub-issue's board kept outside its tracking issue's folder,
which the tracking board cannot link, and a sub-issue's folder kept outside its parent's, which
cannot link the parent's board; on a tracking board, a unit's mirror (`unit.live`, §3) older
than its sub-issue board's `wip.updated`, missing for a unit in progress whose board exists,
differing from that board's run without being older, or left where `embed.js` would clear it,
and a `wip.step` that is a unit's step (`plan`, `branch`, `qa`, `remediation`) rather than the
tracking issue's own phase; on a sub-issue's board, a parent tracking board whose mirror of this
run lags (each fixed by `embed.js`, on either board); with
`--auto`, a page that differs from its template without declaring the divergence (re-render it:
copy the template over it and `embed.js`), and a template not verified since it changed.

## 9. Existing plans and the template

Folders written before this format keep their Markdown; a run that reopens one adds a board
beside it rather than converting it. `plan/examples/38-handshake-empty-name/` is the worked
example, written after the fact. To change the template, edit `plan/template/dashboard.html`,
run `verify/verify-templates.js` once (it verifies the template against the example and the
fixtures in `verify/fixtures/` and records its hash), then copy it over each page and re-embed:
the data lives in `plan.json`, so nothing is lost, and each re-rendered board is again the
verified template plus its data. Never hand-edit a page.
